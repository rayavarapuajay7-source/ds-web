01 / UNDER THE HOOD

Short paths.
Clear ownership.

Kestrel is designed around one simple constraint: every request should do the least possible work between the socket and your data.

REQUEST LIFECYCLEABOUT 4 STEPS

A REQUEST IN FOUR MOVES

From wire to value.

Each stage has a narrow responsibility. That makes performance easier to reason about, profile, and improve.

01

Accept

listener → connection

Non-blocking sockets feed a bounded connection loop. Backpressure is applied before queues become a latency problem.

I/O
02

Decode

bytes → command

The RESP parser reads directly from the input buffer, validating command shape without building redundant strings.

PARSER
03

Resolve

key → shard → value

A stable hash routes the key to its shard. Reads avoid a global lock; writes coordinate only with the owning shard.

MEMORY
04

Reply

value → bytes

Responses are encoded into a reusable output buffer and flushed through the same connection that asked.

I/O

CONCURRENCY MODEL

Work stays
in its lane.

Keys are distributed across independent shards. Each shard owns its table and mutation queue, reducing coordination between unrelated writes.

MEMORY LAYOUT

Keep the useful
bytes close.

A compact in-memory index trades persistence guarantees for speed and simplicity. Know what lives in memory, and size your instance with headroom.

K

Hash index

Average constant-time lookup by key. Shard-local ownership keeps operations predictable.

TTL

Expiration metadata

Optional key lifetimes are checked during reads and cleaned up incrementally.

↔

Bounded buffers

Connection buffers have explicit limits to help contain memory use under slow clients.
